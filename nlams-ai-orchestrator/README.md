# NLAMS 2.0 — Multi-Agent AI Orchestrator

Python/FastAPI microservice implementing the three AI agents from the NLAMS
2.0 blueprint: **Legal Scrutinizer**, **Geospatial Analyzer**, and **R&R
Calculator**, coordinated by a single orchestrator endpoint. This is the
"brain" that plugs into the Node.js core workflow engine.

Tested end-to-end during development against the live Node backend,
including a real generated PDF title deed run through actual text
extraction — not just mocked inputs.

## 1. How it fits together

```
CALA Workbench (frontend)
        |
        v
Node backend  --(X-Service-Key)-->  This service  --(X-Service-Key)--> Node backend
(proposal data)                    (runs 3 agents)                  (saves scrutiny_reports)
```

The Node backend and this service authenticate to each other with a shared
secret (`AI_SERVICE_KEY`), not a user JWT — there's no human "logged in" on
either side of that call. See `src/middleware/serviceAuth.js` and
`src/routes/internal.routes.js` in the Node backend.

## 2. Setup

```bash
pip install -r requirements.txt
cp .env.example .env
```

Set `AI_SERVICE_KEY` in `.env` to **the same value** configured in the Node
backend's `.env` — this handshake will fail otherwise.

`ANTHROPIC_API_KEY` is optional. Without it, the Legal Scrutinizer Agent
falls back to a deterministic regex heuristic (still functional, just less
robust against unusually worded deeds) so the whole pipeline runs without
needing any API key for a demo.

## 3. Run

```bash
uvicorn app.main:app --reload --port 8000
```

Health check: `GET /health`
Interactive API docs (auto-generated by FastAPI): `http://localhost:8000/docs`

## 4. Endpoints

| Method | Route | Purpose |
|---|---|---|
| POST | `/orchestrate/{proposal_id}` | Runs all 3 agents for a proposal, saves the combined report to Node, returns it |
| POST | `/agents/legal-scrutinizer/test` | Standalone: test the Legal Scrutinizer with raw deed text |
| POST | `/agents/geospatial/test` | Standalone: test the Geospatial Analyzer with a parcel list |
| POST | `/agents/rr-calculator/test` | Standalone: test the R&R Calculator with state + parcels |

The standalone endpoints are for demoing each agent in isolation (e.g. in a
pitch) without needing the full Node backend running.

## 5. Agent notes

- **Legal Scrutinizer**: extracts owner name + area from a title deed PDF
  (via `pdfplumber`) and fuzzy-matches the extracted name against what the
  Requiring Body declared for the parcel. Flags on low similarity or on an
  unreadable/missing deed rather than guessing.
- **Geospatial Analyzer**: does *not* re-run the spatial query — the actual
  `ST_Intersects` check happens in Postgres/PostGIS when a parcel is
  created (Node backend). This agent interprets that pre-computed result
  set into a single verdict + summary for the CALA Workbench.
- **R&R Calculator**: deliberately deterministic, no LLM. Compensation math
  has legal/financial consequences and must be reproducible. Uses
  `app/data/state_rr_policy.json` as an illustrative rate schedule — not
  real government figures, swap in actual notified rates for production.

## 6. Known prototype simplifications

- Only the most recent `TITLE_DEED` document per proposal is scrutinized;
  a fuller build would run the legal check per-parcel.
- The R&R policy JSON is illustrative sample data, not sourced from real
  state notifications.
- No retry/queueing — `/orchestrate` is a synchronous call. For a
  production system, this should be an async job (e.g. via a queue) since
  LLM calls and multi-parcel proposals can take a few seconds.
